## Context: The proposal needs an automatic way to measure semantic diversity. Method: We propose to leverage code generation as a domain for studying semantic diversity, since programs have well-defined, executable semantics that can be automatically evaluated. This approach allows us to distinguish between three forms of diversity: lexical (token sequences), syntactic (Abstract Syntax Tree structure), and semantic (program execution outputs). Synthesis: This frames the study by using executable code to operationalize diversity without costly human evaluation.

### Support

The strongest support comes from [(Parisotto et al., 2016-11)](https://www.semanticscholar.org/paper/644ca74f80463415613847ab01cff067fb58f0ad), which uses a Recursive-Reverse-Recursive Neural Network over partial program derivation trees in a string-transformation DSL and accepts sampled programs only when execution on 10 input-output pairs matches the target, showing that executable semantics can serve as an automatic, human-free signal for semantic equivalence; its sampling results, with train/test success rates of 60%/63% for 1-best, 81%/79% for 10 samples, 91%/89% for 50 samples, 94%/94% for 100 samples, and 97%/97% for 300 samples, directly support the plan's use of K=100 sampled programs and execution-output distinctness, although they also show that 100 samples may not fully saturate semantic coverage. Next, [(Korbak et al., 2021-06)](https://www.semanticscholar.org/paper/7c2de353f3151a0f88736af9be354ab5e773bff0) supports the plan's motivation by showing that fine-tuning a 117M-parameter GPT-2-small Python model with KL-DPG or reward baselines changes diversity: compile-only RL increases lexical metrics by producing shorter, simpler programs, while energy-based reward collapses toward a single high-probability compilable sequence, and lexical, AST, and token-frequency metrics must be interpreted together with sequence length, AST node count, and compilation-error categories; this validates the plan's concern that instruction tuning can reduce diversity and that lexical or syntactic metrics alone are insufficient. [(Chen et al., 2023-12)](https://www.semanticscholar.org/paper/08d9019e3084fb4d5d21b342485a1ae4c1dd8129) further supports the AST-plus-execution framing by using VizDoom AST segments and RGB/depth execution observations to infer token substitutions, outperforming baselines by about 9.6% and showing that semantically equivalent programs can differ from gold-identical programs, analogous to the plan's separation of syntactic and semantic diversity. Finally, [(Hui et al., 2024-09)](https://www.semanticscholar.org/paper/11dd2fc88747d20629f5aafab72ba649d93e969c) supports the feasibility of using Qwen-Coder base and instruction-tuned models, since Qwen2.5-Coder is trained on 5.2T tokens with a 70:20:1 code:text:math mixture, 92 languages, and 128K context, and is evaluated against StarCoder2 and DeepSeek-Coder, although it does not report diversity metrics.

### Contradictions

No related work directly refutes the core idea, but the strongest caveat is from [(Parisotto et al., 2016-11)](https://www.semanticscholar.org/paper/644ca74f80463415613847ab01cff067fb58f0ad): its execution-based acceptance is relative to only 10 I/O examples in a 13-instruction DSL, so semantic equivalence on a finite test suite can overstate true generalization; the plan's semantic diversity, defined by differing outputs across test cases, could therefore misclassify programs if the 21 competitive-programming-derived tasks have insufficient, biased, or non-deterministic tests. The next caveat is from [(Korbak et al., 2021-06)](https://www.semanticscholar.org/paper/7c2de353f3151a0f88736af9be354ab5e773bff0): lexical diversity can be artificially inflated when models generate shorter, structurally simpler Python, and reward optimization can collapse token-frequency tails, so the plan's EAD and AST Distinct-N metrics may be confounded unless normalized for sequence length, AST node count, token frequency, and compilability; its Python150 setting, with 150k files, 713k functions, about 250MB of text, a 50k BPE vocabulary, 1000 sampled sequences, and 30% invalid syntax in the original model, also shows that code diversity measurement is sensitive to sampling and syntactic validity. [(Hui et al., 2024-09)](https://www.semanticscholar.org/paper/11dd2fc88747d20629f5aafab72ba649d93e969c) provides a weaker contradiction to the hypothesis rather than the method: it reports that instruction-tuned Qwen2.5-Coder models improve task performance over open-source baselines, but it does not report lexical, syntactic, or execution-output diversity, so the plan cannot assume that instruction tuning necessarily reduces diversity or that performance gains are separable from diversity loss. [(Chen et al., 2023-12)](https://www.semanticscholar.org/paper/08d9019e3084fb4d5d21b342485a1ae4c1dd8129) is the weakest limitation because it does not report dataset size, hardware, hyperparameters, or statistical significance, and its VizDoom setting is indirect evidence that execution-based semantic equivalence differs from syntactic identity rather than a test of LLM instruction-tuning diversity.

### Suggested Action

Most important, strengthen the semantic-diversity evaluation by making execution-based distinctness robust: for each of the 21 tasks, use a fixed, deterministic test suite with multiple hidden, random, and property-based cases, edge cases, timeouts, and Docker resource limits; report execution success, timeout rate, and a saturation curve over sample size because [(Parisotto et al., 2016-11)](https://www.semanticscholar.org/paper/644ca74f80463415613847ab01cff067fb58f0ad) shows 100 samples reaches 94% but 300 reaches 97%, so K=100 per model, yielding 2,100 programs per model across 21 tasks, should be justified or supplemented with K=300 for a subset. Second, normalize and report lexical and syntactic controls following [(Korbak et al., 2021-06)](https://www.semanticscholar.org/paper/7c2de353f3151a0f88736af9be354ab5e773bff0): include sequence length, AST node count, token-frequency tails, compilation-error categories, and length-controlled or structure-controlled EAD and AST Distinct-N, so that diversity changes are not artifacts of shorter or simpler programs. Third, use the planned model lineup and prompt controls while adding explicit baselines and ablations: compare base versus instruction-tuned Qwen2.5-Coder, CodeLlama, Llama-3, Llama-3.1, and commercial models with temperature=1.0, no nucleus sampling, and zero-shot, two-shot, and two-shot chain-of-thought prompts, and report Wilcoxon Signed-Rank tests with Cohen's D and multiple-comparison correction for base versus instruction-tuned, small versus large, prompting, and SFT versus preference tuning comparisons. Fourth, incorporate AST-grounded execution traces and semantic-equivalence checks inspired by [(Chen et al., 2023-12)](https://www.semanticscholar.org/paper/08d9019e3084fb4d5d21b342485a1ae4c1dd8129), such as canonicalized ASTs, segment-level behavior, or pairwise output differences across test cases, to separate syntactic variation from behavioral variation, and treat CodeBERTScore and ICE-Score as secondary neural proxies correlated with execution-output diversity rather than primary semantic measures. Finally, improve reproducibility by documenting Docker images, test-case counts, hardware, sampling seeds, prompt templates, and public code, and by using [(Hui et al., 2024-09)](https://www.semanticscholar.org/paper/11dd2fc88747d20629f5aafab72ba649d93e969c) as a model-release reference for Qwen-Coder evaluation practices while adding the missing diversity metrics.

## Context: The study requires open-ended tasks that allow multiple valid solutions. Method: We will create 21 open-ended programming problems by abstracting competitive programming tasks from CodeNet, ensuring each has sufficient test cases for reliable execution-based evaluation. Synthesis: This creates the task set used to sample model outputs and evaluate diversity across executable programs.

### Support

The strongest support is that CodeNet can be converted into execution-validated tasks with enough tests: [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308) augmented CodeNet C++ test cases with AlphaCode-generated tests, removed tests causing timeouts above 2 minutes, and obtained median 82.5, 75, and 104 test cases per problem in training, validation, and test splits of 1,474, 77, and 41 problems, respectively, with problem-disjoint splits; this directly supports the proposed requirement of sufficient test cases for reliable execution-based evaluation, and its secondary observation that GPT-4 had higher Best@1 but lower Best@8 than GPT-3.5 under the same sampling settings provides preliminary, not definitive, evidence that instruction-tuned models may reduce output diversity. The next strongest support is that CodeNet-derived tasks can be executed safely and compared across base and instruction-tuned models: [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) built a 1,380-problem Python CodeNet benchmark with public and private tests, executed programs in a Judge0 Docker container on an AWS EC2 m7i.large instance, and reported instruction-tuned versus base differences such as CodeLlama instruct 22.5 pass@1 versus base 46.4, showing that CodeNet tasks support executable model comparisons, although the paper measured efficiency rather than diversity. A further strong support is that generated tests can make competitive-programming execution evaluation reliable: [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) combined Codeforces, CodeNet, and Description2Code, added generated tests, increased average tests per problem from 12.4 to 203.7, reduced the false-positive rate from 62% to 4%, and used execution filtering and behavior clustering, with a 41B model solving 31.8% of validation problems at 10@100k and 34.2% at 10@1M. The foundational support is that CodeNet itself is a curated competitive-programming source with processable code: [(Puri et al., 2021-05)](https://www.semanticscholar.org/paper/7547680408358916e66917d03436fca7540a7528) scraped AIZU and AtCoder, filtered C++, Python, and Java submissions, required unique or non-near-duplicate samples, and used tokenizer, structural program tree, and graph filters, providing the raw material for the proposed 21-task abstraction. Additional support comes from [(Prenner, and Robbes, 2023-04)](https://www.semanticscholar.org/paper/70ebcc3716583b7bc0d59e443c83d3ac522b79e9), which mined over 450,000 executable CodeNet buggy/fixed pairs with sandboxed execution and flaky-submission exclusion, and from [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), which sampled n=100 programs per APPS task, executed them against unit tests, and showed that 100-sample execution pipelines are practical on V100-32GB GPUs. Weaker but relevant support includes [(Chen et al., 2024-01)](https://www.semanticscholar.org/paper/208315e64130d7a7eb3562abcf973f27c3329135), which generated semantically different executable Python problems from HumanEval and MBPP-Sanitized and sampled 100 candidates at temperature 0.7, supporting executable problem generation and diversity-oriented evaluation although the excerpt lacks quantitative outcomes; [(Liu et al., 2023-05)](https://www.semanticscholar.org/paper/785bb49af762efd64d841e52aa82c708341a7c43), which used 19,541 CodeNetMut examples from 39 unseen CodeNet problems for execution-trace evaluation; [(Gotmare et al., 2022-07)](https://www.semanticscholar.org/paper/6d994b4f5a46cd14e8f09f1e9e49120546b15e31), which used APPS with 21.2 unit tests per problem and pass@k/n@k execution evaluation; [(Li et al., 2023-05)](https://www.semanticscholar.org/paper/d53f4cdddd7494d5f6e64d81f627691f6d7dff95), which used generated tests to reduce false positives on CodeContests and APPS; and [(Mirzayanov et al., 2020-12)](https://www.semanticscholar.org/paper/c630fc6d24122590cd2cc7ccf96c03222e77beb3), which provides contest-task validation infrastructure such as generators, checkers, validators, and automated testing, although it does not address LLM sampling or diversity.

### Contradictions

The strongest contradiction is that none of the related work directly validates the proposed 21-task open-ended abstraction of CodeNet for diversity measurement; most preserve original competitive-programming statements or use closed-ended tasks. [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308) retained original CodeNet problems for performance optimization, [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) used original CodeNet problems for efficiency optimization, [(Prenner, and Robbes, 2023-04)](https://www.semanticscholar.org/paper/70ebcc3716583b7bc0d59e443c83d3ac522b79e9) used buggy/fixed repair pairs, [(Liu et al., 2023-05)](https://www.semanticscholar.org/paper/785bb49af762efd64d841e52aa82c708341a7c43) used execution-trace prediction, [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) and [(Li et al., 2023-05)](https://www.semanticscholar.org/paper/d53f4cdddd7494d5f6e64d81f627691f6d7dff95) used original CodeContests or APPS problems, and [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44) and [(Gotmare et al., 2022-07)](https://www.semanticscholar.org/paper/6d994b4f5a46cd14e8f09f1e9e49120546b15e31) used APPS. Therefore, abstracting CodeNet tasks into canonical open-ended prompts may change task semantics, invalidate original hidden tests, or create tasks that appear open-ended but are still overconstrained by the test suite. The next strongest contradiction is that 21 tasks is smaller than comparable executable evaluation sets, which may make task-level diversity estimates unstable and underpowered for Wilcoxon Signed-Rank Tests and Cohen's D: [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) used 165 CodeContests test problems, [(Liu et al., 2023-05)](https://www.semanticscholar.org/paper/785bb49af762efd64d841e52aa82c708341a7c43) used 39 unseen CodeNet problems, [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308) used 41 test problems, [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) used 1,380 problems, and [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44) and [(Gotmare et al., 2022-07)](https://www.semanticscholar.org/paper/6d994b4f5a46cd14e8f09f1e9e49120546b15e31) used APPS test sets of 5,000 problems. A further contradiction is that lexical and syntactic surface metrics may not capture semantic diversity: [(Puri et al., 2021-05)](https://www.semanticscholar.org/paper/7547680408358916e66917d03436fca7540a7528) found bag-of-tokens MLP code-similarity accuracy below 87% on all four benchmarks, indicating token-frequency features alone were insufficient, and [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) relied on execution-behavior clustering rather than surface similarity, suggesting that EAD and AST Distinct-N metrics could be confounded by superficial code style. Another important contradiction is that K=100 may be insufficient for hard CodeNet tasks: [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) sampled up to 1,000,000 programs per problem and used clustering to obtain 31.8% to 34.2% solve rates, while [(Gotmare et al., 2022-07)](https://www.semanticscholar.org/paper/6d994b4f5a46cd14e8f09f1e9e49120546b15e31) used k=1000 for APPS, whereas [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44) used 100 samples for ranking rather than diversity, so rare semantically distinct programs may be missed at K=100. Sampling temperature is also not validated: the proposed temperature 1.0 without nucleus sampling differs from [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), which used 0.8 for Codex and 0.9 for GPT-J/GPT-Neo, [(Chen et al., 2024-01)](https://www.semanticscholar.org/paper/208315e64130d7a7eb3562abcf973f27c3329135), which used 0.7, and [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), which used 0.25 for an APPS comparison, so diversity outcomes may be sampling-dependent. Finally, CodeNet language and execution constraints are heterogeneous: [(Puri et al., 2021-05)](https://www.semanticscholar.org/paper/7547680408358916e66917d03436fca7540a7528) covered C++, Python, and Java, [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308) focused on C++ with GCC 9.3.0, C++17, -O3, and gem5 timing, and [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) focused on Python 3, so a 21-task set must control language, compiler, timeouts, and false positives to avoid confounding diversity with executability.

### Suggested Action

The most important action is to validate open-endedness before finalizing the 21 tasks: for each candidate CodeNet problem, collect multiple accepted submissions, execute them on public, private, and generated tests, cluster programs by execution behavior, and require at least two or three distinct behavior clusters plus human confirmation that the canonical prompt admits multiple valid algorithms; discard or repair tasks where the test suite overconstrains the solution, using the behavior-clustering motivation from [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) and the CodeNet test-augmentation evidence from [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308). The next most important action is to address the small task count: if feasible, expand the set to at least 39 to 41 tasks to match [(Liu et al., 2023-05)](https://www.semanticscholar.org/paper/785bb49af762efd64d841e52aa82c708341a7c43) and [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308), or, if 21 tasks is fixed, report exact Wilcoxon p-values, Cohen's D, bootstrap confidence intervals, a power analysis, and task-level random effects to avoid overinterpreting a small case study. Third, build a robust execution and test protocol: add generated tests, differential tests, timeout and memory limits, and measure false-positive rates, targeting test densities comparable to the median 82.5 tests per problem in [(Shypula et al., 2023-02)](https://www.semanticscholar.org/paper/1786a2f9140ed7211b21302977de64e948b92308) or the 203.7 tests per problem and 4% false-positive rate in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), and use Docker or Judge0 isolation as in [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) and [(Prenner, and Robbes, 2023-04)](https://www.semanticscholar.org/paper/70ebcc3716583b7bc0d59e443c83d3ac522b79e9). Fourth, add sampling ablations: keep K=100 as the primary setting because of [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44) and [(Chen et al., 2024-01)](https://www.semanticscholar.org/paper/208315e64130d7a7eb3562abcf973f27c3329135), but also report saturation curves for K=500 or K=1000 and temperatures 0.7, 0.8, and 1.0 with and without nucleus sampling, because sample budget and temperature materially affect code-generation outcomes in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) and [(Gotmare et al., 2022-07)](https://www.semanticscholar.org/paper/6d994b4f5a46cd14e8f09f1e9e49120546b15e31). Fifth, make semantic execution diversity the primary metric, using pairwise output distinctness and behavior clustering, while treating lexical EAD, AST Distinct-N, CodeBERTScore, and ICE-Score as secondary and reporting correlations among them, following the caution from [(Puri et al., 2021-05)](https://www.semanticscholar.org/paper/7547680408358916e66917d03436fca7540a7528) that token-frequency features alone were insufficient for code similarity. Sixth, add contamination controls: select temporally held-out or otherwise unseen CodeNet problems, use problem-disjoint splits, and report n-gram overlap with likely training data, as motivated by the temporal split in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) and the problem-disjoint CodeNet splits in [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f). Finally, standardize prompt templates and function signatures while verifying that base models can parse the canonical format, include input/output demonstrations where needed, and use a Polygon-like validation checklist for generators, checkers, validators, and automated tests as described by [(Mirzayanov et al., 2020-12)](https://www.semanticscholar.org/paper/c630fc6d24122590cd2cc7ccf96c03222e77beb3).

## Context: The research question requires measuring diversity at multiple levels. Method: To measure diversity, we will implement several metrics:
- **Semantic diversity**: Programs are considered semantically distinct if their outputs differ across test cases
- **Lexical diversity**: Using Expectation-Adjusted Distinct n-grams (EAD) on tokenized programs
- **Syntactic diversity**: Adapting Distinct-N metrics to canonicalized Abstract Syntax Trees
- **Neural diversity**: Using existing code evaluation models like CodeBERTScore and ICE-Score
Synthesis: This supplies the measurement instruments needed to test whether instruction tuning reduces lexical, syntactic, semantic, or neural diversity.

### Support

The strongest support for the proposed neural-diversity component comes from [(Zhou et al., 2023-02)](https://www.semanticscholar.org/paper/31366ff634fc905affd78dbd8ddc9a872c006a87), which evaluates CodeBERTScore on HumanEval development sets for Java, C++, JavaScript, and Python and shows that language-specific CodeBERT models generally outperform CodeBERT-base, that layer ablations report average Kendall-Tau and Spearman correlations in the approximate 0.25 to 0.45 range across layers 0 through 12, and that adding natural-language context improves Kendall-Tau from 0.50 to 0.52. Its qualitative examples, such as aligning shutil.rmtree with os.rmdir and math.sqrt(x) with x ** 0.5, directly support repurposing CodeBERTScore from pairwise similarity to pairwise distinctness among the 100 generated programs per open-ended problem, provided the plan selects language-specific models, a pre-final layer, and optionally includes the task instruction. The next strongest support is [(Zhuo, 2023-04)](https://www.semanticscholar.org/paper/fbe90d2864ffdbefd1fc0a7c6f65ac10452052f2), which validates ICE-Score as an LLM-based code evaluation signal on CoNaLa, a dataset of 2,860 annotated code snippets from 472 examples with 5 generations per example and about 4.5 annotators per snippet, and on HumanEval-X execution-based correctness across Java, C++, Python, and JavaScript. ICE-Score achieved example-level Kendall tau 0.556, Pearson 0.613, and Spearman 0.594, and corpus-level Kendall tau 0.546, Pearson 0.649, and Spearman 0.635, outperforming BLEU, CodeBLEU, chrF, ROUGE-L, METEOR, RUBY, and CodeBERTScore variants, while CoT-Ref-ICE-Score reached corpus-level Kendall tau 0.583, Pearson 0.712, and Spearman 0.667. Although this work evaluates quality and correctness rather than diversity, it supports including ICE-Score as a complementary neural instrument, especially with chain-of-thought prompting and reference-free evaluation. A further support for syntactic diversity is [(Ma et al., 2023-05)](https://www.semanticscholar.org/paper/2c933b2a293a1cceb69236d89db06addf5cc7c74), which uses AST normalization and syntax-evaluation pipelines on 291 programs in C, Java, Python, and Solidity, with 3,124 extracted samples and 206,913 LOC, and reports AST pass rates above 90%, Hit@10 of 84-100%, and high human-human agreement with Cohen's kappa 0.844-0.936 and Gwet's AC1 0.914-0.975. This supports the proposed adaptation of Distinct-N to canonicalized ASTs, because normalization can reduce representation variance before structural comparison. Support for lexical EAD is methodological rather than direct: [(Papineni et al., 2002-07)](https://www.semanticscholar.org/paper/d7da009f457917aa381619facfa5ffae9329a6e9) shows tokenized n-gram precision can separate human from machine translations on a 500-sentence Chinese-to-English corpus, with all n-gram precisions producing the same system ranking and block-wise paired t-tests over 20 blocks of 25 sentences, and BLEU correlating 0.99 with monolingual and 0.96 with bilingual human judgments from 10 judges in each group. This supports using tokenized n-gram distinctness as a lexical signal and using block-wise or paired statistical tests, although BLEU is reference-based precision rather than reference-free distinctness. The weakest support is [(Liu et al., 2023-12)](https://www.semanticscholar.org/paper/41113411e1748a34bb80f12c761b7af1ed6dbb90), which uses an embedding-based REPR filter for instruction-tuning data selection with 6K and 10K budgets on LLaMA-1-13B, LLaMA-2-13B, and Mistral-7B, and therefore supports the broader idea that learned representations can operationalize diversity, but the excerpt provides no quantitative diversity-filter results and does not measure generated code diversity.

### Contradictions

The strongest contradiction to the proposed neural-diversity plan comes from [(Zhan et al., 2024-07)](https://www.semanticscholar.org/paper/2481f5378159eb053583b261b2515d85006f4515), which shows CodeBERTScore achieved only 54.82 percent AUC on the Spider-Pair test-aug SQL dataset, indicating weak performance when pretrained code evaluation models are applied to a different code domain. The same paper reports that CodeScore was the best baseline, with test-aug AUC only 1.5 percentage points below the proposed graph-based method, while SPES achieved 72.7 percent and 65.85 percent AUC on the two test datasets, and GPT-4 still performed below the proposed method. This contradicts any assumption that CodeBERTScore is a domain-robust neural diversity instrument for the proposed 21 open-ended programming problems without target-domain validation. The next strongest contradiction is that [(Zhuo, 2023-04)](https://www.semanticscholar.org/paper/fbe90d2864ffdbefd1fc0a7c6f65ac10452052f2) validates ICE-Score for code usefulness and functional correctness, not diversity, and reports no statistical significance tests or diversity-specific outcomes. Its reference-enhanced variant may introduce bias because the reference code had an average human usefulness score of 3.4 out of 4, and its evaluation used GPT-3.5-turbo at temperature 0 with template-based criteria rather than generated criteria. Therefore, using ICE-Score as a neural diversity metric without a dedicated pairwise-distinctness prompt, reference-free design, and validation against execution outputs is not supported by this work. A further contradiction is that [(Zhou et al., 2023-02)](https://www.semanticscholar.org/paper/31366ff634fc905affd78dbd8ddc9a872c006a87) reports only modest correlations for CodeBERTScore, with layer ablation correlations in the approximate 0.25 to 0.45 range and a small context improvement from Kendall-Tau 0.50 to 0.52, and that language-specific models generally outperform CodeBERT-base. This contradicts a naive use of a default CodeBERTScore configuration, such as the base model or final layer, as a reliable semantic-diversity proxy for all programming languages in the plan. The proposed syntactic metric also faces a caveat from [(Ma et al., 2023-05)](https://www.semanticscholar.org/paper/2c933b2a293a1cceb69236d89db06addf5cc7c74), where human-machine agreement was low, with Cohen's kappa of 0.25-0.38, attributed to prevalence effects in imbalanced pass/fail data, even though human-human agreement was high. This contradicts relying solely on automated AST-based distinctness without expert adjudication and prevalence-corrected agreement metrics. A weaker contradiction is that [(Papineni et al., 2002-07)](https://www.semanticscholar.org/paper/d7da009f457917aa381619facfa5ffae9329a6e9) demonstrates n-gram metric validation at the system level using only five aggregate points, with correlations of 0.99 and 0.96, and emphasizes reference dependence; this warns that lexical EAD may track surface form rather than semantic diversity and should not be treated as sufficient evidence of semantic distinctness. The weakest caveat is that [(Liu et al., 2023-12)](https://www.semanticscholar.org/paper/41113411e1748a34bb80f12c761b7af1ed6dbb90) does not provide quantitative results for its diversity filter in the supplied excerpt and applies embedding-based diversity to instruction-tuning data selection rather than generated code, so it cannot by itself support the proposed measurement protocol.

### Suggested Action

The most important action is to add a target-domain validation phase for the neural diversity instruments before the main instruction-tuning comparison. For each of the 21 open-ended problems, generate a pilot set of 100 programs per model at temperature 1.0, execute them in Docker, and compute pairwise CodeBERTScore and ICE-Score distinctness, then correlate these scores with execution-based semantic diversity and, if feasible, human judgments using Kendall tau, Spearman, Pearson, and AUC for distinguishing semantically distinct programs. This should include language-specific CodeBERT models where available, a layer ablation around the pre-final layers identified by [(Zhou et al., 2023-02)](https://www.semanticscholar.org/paper/31366ff634fc905affd78dbd8ddc9a872c006a87), and an ablation of whether the natural-language task instruction is included, because context improved Kendall-Tau from 0.50 to 0.52. The second most important action is to redesign ICE-Score specifically for diversity rather than reusing its quality/correctness prompt: use a reference-free pairwise prompt that asks whether two programs implement different behaviors or solutions, add chain-of-thought reasoning, keep temperature 0, aggregate multiple judgments if possible, and explicitly test for reference bias because [(Zhuo, 2023-04)](https://www.semanticscholar.org/paper/fbe90d2864ffdbefd1fc0a7c6f65ac10452052f2) found reference code may bias scores. The third action is to strengthen the semantic diversity metric by defining output equivalence carefully: normalize outputs, handle non-determinism, timeouts, side effects, and partial correctness, and report both pass/fail diversity and output-space distinctness across all test cases, because execution-based semantics is the main advantage of the code-generation plan and is not captured by lexical or neural surface metrics. The fourth action is to make lexical EAD more defensible by specifying tokenization, n-gram range, expectation adjustment, and sample-size invariance, and by validating it against human lexical-diversity judgments or at least by reporting block-wise variance and paired Wilcoxon tests with Cohen's D, following the block-wise paired-test logic in [(Papineni et al., 2002-07)](https://www.semanticscholar.org/paper/d7da009f457917aa381619facfa5ffae9329a6e9). The fifth action is to canonicalize ASTs before computing Distinct-N, using normalization techniques similar to [(Ma et al., 2023-05)](https://www.semanticscholar.org/paper/2c933b2a293a1cceb69236d89db06addf5cc7c74), and to validate the syntactic metric with expert adjudication and prevalence-corrected agreement such as Gwet's AC1, because that work found human-machine Cohen's kappa of only 0.25-0.38 in imbalanced structural evaluation. The least urgent but still useful action is to add an auxiliary embedding-based redundancy measure inspired by [(Liu et al., 2023-12)](https://www.semanticscholar.org/paper/41113411e1748a34bb80f12c761b7af1ed6dbb90), such as nearest-neighbor embedding distance or a thresholded redundancy filter, but only after quantitative validation on the code-generation dataset, since the related work does not provide numerical evidence for its diversity filter and is not code-specific.

## Context: Diversity scores must be comparable across different sample sizes. Method: We will adopt a pairwise diversity metric that computes the average distinctness over all program pairs to ensure invariance to sample size, addressing potential confounds in diversity measurement. Synthesis: This ensures that observed diversity differences are not confounded by the number of generated programs.

### Support

Read as an iterative line of work, the strongest support comes from [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), which defines Sim@K as an average over all pairwise code similarities for K sampled programs and evaluates it on APPS and HumanEval with 50 problems per dataset at K=10. This is directly aligned with the proposed pairwise average distinctness over all program pairs and with the plan's code-generation setting, temperature=1.0 sampling, and comparison of prompting strategies; the paper also reports that higher temperature decreased Sim@10 and CSim@10, that filtering to functionally correct programs lowered CSim@10, and that few-shot chain-of-thought and planning increased Sim@10 while planning reduced Pass@1, all of which justify the plan's focus on temperature, prompting, correctness, and diversity trade-offs. The next strongest support is from [(Li et al., 2015-10)](https://www.semanticscholar.org/paper/651e5bcc14f14605a879303e97572a27ea8c7956), which introduced distinct-1 and distinct-2 as distinct unigram/bigram counts divided by total generated tokens and used them with BLEU on large conversational datasets, including a Twitter set of 23 million snippets from 129 million context-message-response triples with 2,118 development and 2,114 test conversations, and an OpenSubtitles/IMDb setup with 2,000 development and 2,000 test pairs restricted to 6-18 tokens. Although the paper does not provide numeric distinct values, it shows that corpus-level distinct-n is a useful but length- and sample-sensitive diversity signal, supporting the plan's concern that lexical and syntactic diversity metrics need explicit control for sample size and length. A weaker but relevant support is [(Gao et al., 2021-04)](https://www.semanticscholar.org/paper/c26759e6c701201af2f62f7ee4eb68742b5bf085), which uses pairwise embedding similarity, uniformity, alignment, and cosine-similarity distributions to characterize sentence distinguishability and reports that unsupervised SimCSE-BERT base improved average Spearman correlation across STS12-STS16, STS-B, and SICK-R from 72.05 to 76.25, while supervised SimCSE-BERT base reached 81.57 and supervised SimCSE-RoBERTa large reached 83.76. This supports the plan's neural diversity idea of using pairwise semantic similarity from code models, but it is limited to sentence embeddings and does not test code execution or sample-size invariance. The weakest support is [(Zhang et al., 2024-04)](https://www.semanticscholar.org/paper/522240c89c7ac6b1365e8308c6a88c4784adc62e), which studies LLM-output diversity for commonsense generation using GPT-3.5-turbo and Vicuna-13b-v1.5 at temperature 1.0 and maximum length 25 tokens, and trains BART-large mixture-of-experts models on 210,846 ICD-generated CommonGen sentences with three experts, k=3, 20 epochs, batch size 64, learning rate 3e-5, beam size 5, and a single RTX A6000 GPU. It supports the broader premise that diversity can be measured and improved in LLM outputs, but it uses natural-language sentences, a much smaller k=3, and does not provide a pairwise, sample-size-invariant code metric.

### Contradictions

The strongest contradiction is that the closest prior method, [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), uses the same average-over-all-pairs structure but does not test invariance across different K values; it evaluates Sim@10 and CSim@10 only at K=10 on 50 APPS and 50 HumanEval problems, so it does not establish that the average pairwise score remains stable when K changes from 10 to 100 or across model families. This directly undermines the proposed method's claim that pairwise averaging ensures sample-size invariance, because finite-sample pairwise averages can vary with K, especially when programs are duplicated, correlated, or filtered for correctness, as the paper's CSim@10 shows. A second important contradiction is that the same paper found embedding-based CodeBERT had no significant correlation with human judgments, reported as approximately 0.50, while reasoning-based LLM evaluation had the highest Pearson correlation, up to 25 percent higher than other automatic pairwise measures; this contradicts an overreliance on CodeBERTScore or similar embedding-based neural diversity metrics in the plan unless they are validated against execution-based or human judgments. The next contradiction is from [(Li et al., 2015-10)](https://www.semanticscholar.org/paper/651e5bcc14f14605a879303e97572a27ea8c7956), which shows that distinct-n metrics are corpus-level and scaled by total tokens rather than pairwise, and that diversity can be entangled with generation quality and beam size, as evidenced by MMI-bidi BLEU scores of 5.90, 5.86, and 5.76 at beam sizes 200, 50, and 20 versus 4.44 for machine translation with neural reranking. If the plan's lexical or syntactic pairwise distinctness is derived from distinct-n or n-gram overlap without length normalization and sample-size validation, it may inherit the same confounds that motivate the proposed method. A weaker contradiction is that [(Gao et al., 2021-04)](https://www.semanticscholar.org/paper/c26759e6c701201af2f62f7ee4eb68742b5bf085) uses pairwise embedding similarity and uniformity to characterize distinguishability but does not demonstrate invariance to sample size, so the plan's assumption that neural pairwise similarity will be comparable across K=100 samples is not directly supported. The weakest contradiction is [(Zhang et al., 2024-04)](https://www.semanticscholar.org/paper/522240c89c7ac6b1365e8308c6a88c4784adc62e), which evaluates diversity with k=3 generated sentences per input and reports inference times of 5-6 hours for CommonGen, 2-3 hours for ComVE, and 1-2 hours for DimonGen, with GPT-3.5-turbo costs of about $6, $4, and $4, but does not provide a sample-size-invariant metric; this suggests that diversity findings can be sensitive to the chosen k and generation pipeline, making direct transfer to the plan's K=100 code setting uncertain.

### Suggested Action

Most important, the plan should not assert that pairwise averaging guarantees sample-size invariance; instead, it should validate invariance empirically by subsampling the K=100 programs per prompt into K=10, 20, 50, and 100, recomputing each pairwise metric, and reporting the mean, standard deviation, bootstrap confidence intervals, and U-statistic variance or rarefaction curves, with a pre-registered threshold for acceptable drift. Next, the plan should define each pairwise distinctness score explicitly and bound it to [0,1]: semantic distinctness as the fraction of test cases where two programs produce different outputs, with a fixed rule for timeouts, errors, and non-determinism; lexical distinctness as 1 minus a length-normalized token n-gram similarity or an EAD-based pair score; syntactic distinctness as 1 minus a normalized AST edit distance or tree-kernel similarity; and neural distinctness as 1 minus CodeBERTScore or ICE-Score, while reporting duplicate rates and length distributions. A high priority is to stratify diversity by correctness, following [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), by reporting all-program diversity, correct-program diversity analogous to CSim@K, and a diversity-weighted correctness score analogous to DPass@K, because the paper found that filtering to correct programs changed CSim@10 and that planning reduced Pass@1. The plan should also treat execution-based semantic diversity as the primary metric and use CodeBERTScore, ICE-Score, and any LLM judge as secondary, because [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) found CodeBERT had no significant human correlation while reasoning-based LLM evaluation correlated best; if an LLM judge is used, report model, prompt, cost, and agreement with execution-based labels. Prompting should be analyzed as an interaction term rather than a nuisance variable, since [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) showed chain-of-thought and planning increased Sim@10, meaning CoT may reduce diversity and confound comparisons between base and instruction-tuned models. Finally, the statistical and computational protocol should be made reproducible by fixing random seeds, Docker resource limits, timeouts, and temperature=1.0 without nucleus sampling; using problem-level clustering or mixed-effects models in addition to Wilcoxon Signed-Rank Tests and Cohen's D; correcting for multiple comparisons across models, prompts, and metric types; and reporting hardware, wall-clock time, and API costs if commercial models or LLM judges are used, especially because [(Zhang et al., 2024-04)](https://www.semanticscholar.org/paper/522240c89c7ac6b1365e8308c6a88c4784adc62e) shows that diversity pipelines can be expensive and sensitive to k, model, and generation settings.

## Context: The central hypothesis concerns instruction tuning effects across model families. Method: We plan to evaluate LLAMA-3, LLAMA-3.1, CodeLLAMA, and Qwen-Coder models, which represent different instruction tuning strategies (PPO+DPO+Rejection Sampling, DPO+Rejection Sampling, SFT only). We will also create additional SFT checkpoints using MagiCoder's OSS-Instruct dataset. Commercial models (OpenAI GPT variants, Anthropic Claude) will provide additional comparison points. Synthesis: This provides the model set needed to isolate the effect of instruction tuning on diversity.

### Support

The strongest support for the proposed method is that executable competitive-programming tasks can provide an automatic semantic signal for code generation, and that sample diversity can be manipulated and measured through execution behavior. [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) pretrains 300M-41B transformers on GitHub, fine-tunes on CodeContests from Codeforces, Description2Code, and CodeNet, samples k=1k-1M programs, filters by example tests, clusters by execution behavior, and reports 10@k solve rates; its 41B clustered model reaches 10@1k 21.0% and 10@100k 31.8% validation, and random metadata such as tags/ratings improves solve rate, directly supporting the plan's use of competitive-programming-derived tasks, executable tests, and large sample sets to study semantic diversity. A second, newer line of work supports the plan's model and instruction-tuning comparisons: [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84) generates MAGPIE instruction data with Llama-3-8B/70B-Instruct, fine-tunes Llama-3-8B, Qwen1.5, Qwen2, and Llama-3.1-Minitron with SFT and DPO using 300K SFT and 100K preference instances on four A100-SXM4-80GB GPUs with vLLM and bfloat16, and analyzes instruction coverage with all-mpnet-base-v2 embeddings, showing that synthetic SFT/DPO checkpoints can be built and compared across Llama and Qwen families, which is close to the plan's Llama-3/Llama-3.1/Qwen-Coder and SFT-checkpoint design. This is consistent with older instruction-tuning evidence that SFT can improve code: [(Li et al., 2023-03)](https://www.semanticscholar.org/paper/7bf72a3b5fbac8bc0f461780810fbc781c28ef53) progressively fine-tunes LLaMA-7B on CAMEL Code/Math/Science data and reports HumanEval/HumanEval+ gains over base LLaMA-7B and Vicuna-7B, although without diversity metrics. Preference-tuning evidence also supports the plan's focus on DPO: [(Ivison et al., 2023-11)](https://www.semanticscholar.org/paper/37680e5cb6030e01f1a44a5abe2257972196ae26) trains TULU 2 with DPO on a 512-core TPUv3 for about 7 days over 3 epochs, finds DPO improves AlpacaEval/MT-Bench while leaving MMLU/BBH/GSM8K largely unchanged, and shows Code Llama-based Code TULU 2 outperforms Llama-2-based TULU 2 on CodexEval, supporting the need to compare code-specialized and preference-tuned checkpoints. Weaker but still relevant support comes from semantic-dispersion and controlled-code work: [(Yang et al., 2024-06)](https://www.semanticscholar.org/paper/feaa5ce215053aa08cc46ea9756e90b7950dca68) measures nearest-neighbor embedding dispersion and finds reference-based responses less dispersed than direct responses, providing a non-code precedent for measuring semantic diversity after instruction tuning; [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f) compares CodeLlama, Llama, GPT-3.5/GPT-4 on a 204-program Java/JML benchmark with runtime tests, supporting controlled code-task evaluation and commercial-model comparison; [(Zhang et al., 2024-06)](https://www.semanticscholar.org/paper/86905d23c2d1c9386f3eb063132c14119ed79e5c) uses K=20 executable candidates and test-case pass/fail to build preference data, supporting execution-based code evaluation; and [(Dissanayake et al., 2024-04)](https://www.semanticscholar.org/paper/ce9c85b3103619669cc7220e5a081f2393e0318a) provides a weaker SFT/DPO checkpoint-construction precedent for small open LLaMA models. Iteratively, the 2022 code-sampling work establishes executable semantic signals, the 2023 SFT/DPO work establishes instruction-tuning effects, and the 2024 work extends this to Llama-3/Qwen synthetic data, semantic dispersion, and controlled code benchmarks, collectively supporting the plan's core design even though none directly measures EAD, AST distinctness, CodeBERTScore, or ICE-Score for code diversity after instruction tuning.

### Contradictions

The strongest contradiction is that the plan's semantic-diversity metric is not validated by the related work, and execution-based semantic distinction can be confounded by incomplete tests. [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) reports that cleaned CodeContests still has a 4% false-positive rate and 46% false-positive-or-slow rate, versus 62%/88% raw, 60% APPS, and 30% HumanEval, showing that pass/fail on limited tests can misclassify programs; if the plan's 21 open-ended problems have insufficient test coverage, programs with different outputs may be incorrectly treated as semantically equivalent or distinct. This is reinforced by [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f), which uses 204 Java programs with average 15.10 test cases, 95.54% branch coverage, and 93.34% line coverage, indicating that reliable execution-based code evaluation requires substantial test coverage and controlled specifications, whereas the plan does not yet specify coverage thresholds. A second contradiction is scale: the plan uses K=100 programs and 21 problems, while related code-generation work shows that sample budget and task count materially affect outcomes. [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) evaluates k=1k, 10k, 100k, and 1M samples, with 41B clustered 10@k increasing from 21.0% at 1k to 34.2% at 1M validation, and uses 117 validation and 165 test problems; [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f) uses 204 programs; [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84) uses 300K SFT and 100K preference instances. The plan's 2,100 programs per model may be too small to estimate rare semantic modes or to stabilize pairwise diversity estimates, especially if diversity is computed only over 21 prompts. A third contradiction is that none of the cited works directly compares the exact proposed model/recipe set—Llama-3 PPO+DPO+Rejection Sampling, Llama-3.1 DPO+Rejection Sampling, CodeLlama SFT-only, and Qwen-Coder—under a common code-diversity protocol, and no Anthropic Claude comparison is provided; [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84) uses Llama-3/Qwen SFT/DPO but not Qwen-Coder or the plan's MagiCoder SFT checkpoints, and [(Ivison et al., 2023-11)](https://www.semanticscholar.org/paper/37680e5cb6030e01f1a44a5abe2257972196ae26) uses Code Llama and Llama-2 TULU models rather than the exact proposed family. A fourth contradiction is that instruction tuning does not necessarily reduce diversity in the related work; it often improves task performance or coverage. [(Ivison et al., 2023-11)](https://www.semanticscholar.org/paper/37680e5cb6030e01f1a44a5abe2257972196ae26) reports DPO improves AlpacaEval/MT-Bench without large changes to MMLU/BBH/GSM8K, and Code Llama-based Code TULU 2 outperforms Llama-2-based TULU 2 on CodexEval; [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84) reports MAGPIE SFT/DPO improves AlpacaEval 2 and Arena-Hard, and its instruction-embedding coverage is broader than several baselines; [(Li et al., 2023-03)](https://www.semanticscholar.org/paper/7bf72a3b5fbac8bc0f461780810fbc781c28ef53) reports CAMEL SFT improves HumanEval/HumanEval+. These findings contradict a blanket assumption that preference tuning or SFT will simply collapse diversity, and they require the plan to measure diversity rather than infer it from alignment quality. A fifth contradiction is decoding and prompt sensitivity: [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f) uses greedy decoding with top_k=1 and temperature=0, and finds few-shot prompting changes performance, showing that diversity results can be confounded by decoding and prompt template if not ablated; the plan's temperature=1.0 without nucleus sampling is reasonable for exposing stochastic variation, but related work does not validate that this setting is optimal for code correctness or diversity. Weaker contradictions include the absence of code-specific diversity metrics in most related work: [(Dissanayake et al., 2024-04)](https://www.semanticscholar.org/paper/ce9c85b3103619669cc7220e5a081f2393e0318a) and [(Zhang et al., 2024-06)](https://www.semanticscholar.org/paper/86905d23c2d1c9386f3eb063132c14119ed79e5c) do not report lexical, syntactic, AST, CodeBERTScore, ICE-Score, or execution-output diversity, and [(Yang et al., 2024-06)](https://www.semanticscholar.org/paper/feaa5ce215053aa08cc46ea9756e90b7950dca68) uses natural-language embedding dispersion rather than executable code semantics, so the plan's metric suite remains under-validated.

### Suggested Action

The most important action is to validate the semantic-diversity metric before interpreting instruction-tuning effects. The plan should report test-case coverage, false-positive/false-negative rates, and behavioral clustering of execution outputs, following [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), which uses example-test filtering and execution-behavior clustering, and [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f), which uses 204 Java programs with average 15.10 test cases, 95.54% branch coverage, and 93.34% line coverage. Concretely, for each of the 21 CodeNet-derived problems, include multiple hidden test cases, branch/line coverage targets, timeout/memory limits in Docker, and a secondary semantic-diversity estimate based on clustering programs by output equivalence; report how many program pairs are semantically distinct under the full test suite versus a smaller test subset. The second most important action is to increase or ablate sample budget and task count. Because [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) shows solve rate continues to improve from k=1k to 1M and uses 117 validation/165 test problems, the plan should either expand beyond 21 problems or report diversity saturation curves at K=10, 50, 100, 500, and 1000 where compute allows, with bootstrap confidence intervals for pairwise distinctness. This will show whether K=100 is sufficient to capture semantic modes. The third action is to make the instruction-tuning comparison more controlled by pairing base and tuned checkpoints within the same architecture and by adding SFT data controls. The plan's use of MagiCoder OSS-Instruct SFT checkpoints is supported by synthetic-data SFT/DPO pipelines such as [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84), which fine-tunes Llama-3-8B, Qwen1.5, Qwen2, and Llama-3.1-Minitron with 300K SFT and 100K DPO data, and by [(Dissanayake et al., 2024-04)](https://www.semanticscholar.org/paper/ce9c85b3103619669cc7220e5a081f2393e0318a), which constructs SFT/DPO checkpoints for Open-LLaMA 3B. The plan should report exact checkpoint names, parameter counts, training data sizes, optimizer/hyperparameters, and whether SFT checkpoints are trained from the same base as Llama-3/Llama-3.1/CodeLlama/Qwen-Coder; it should also include a non-code or code-specific SFT control to separate data effects from alignment effects. The fourth action is to add performance controls so diversity is not confounded with correctness or verbosity. Related work shows instruction tuning can improve code or instruction-following quality: [(Li et al., 2023-03)](https://www.semanticscholar.org/paper/7bf72a3b5fbac8bc0f461780810fbc781c28ef53) reports HumanEval/HumanEval+ gains, [(Ivison et al., 2023-11)](https://www.semanticscholar.org/paper/37680e5cb6030e01f1a44a5abe2257972196ae26) reports DPO and Code TULU 2 CodexEval gains, and [(Zhang et al., 2024-06)](https://www.semanticscholar.org/paper/86905d23c2d1c9386f3eb063132c14119ed79e5c) uses executable pass/fail signals. The plan should report pass@1, pass@10, solve rate, syntax-error rate, execution-timeout rate, and length/token counts alongside EAD, AST distinctness, CodeBERTScore, and ICE-Score, and use partial correlations or regression to adjust diversity for correctness and length. The fifth action is to strengthen statistical and reproducibility details. The plan already uses Wilcoxon Signed-Rank Tests and Cohen's D, but it should add bootstrap confidence intervals for pairwise diversity, multiple-comparison correction across models/prompts/metrics, and Docker environment details such as Python version, CPU/memory limits, timeout, and random seeds. For commercial models, report API version, temperature, max tokens, and whether nucleus sampling is available, because [(Ma et al., 2024-09)](https://www.semanticscholar.org/paper/0f4095d36908b68299f251c7c1774479b9e0b84f) shows decoding and prompt template materially affect code-task performance. A less important but useful action is to use instruction-coverage and semantic-dispersion analyses as auxiliary diagnostics, following [(Xu et al., 2024-06)](https://www.semanticscholar.org/paper/cab3d65b3f4d0a4169d0fdaaed15af6be1d6bb84) for embedding-based coverage and [(Yang et al., 2024-06)](https://www.semanticscholar.org/paper/feaa5ce215053aa08cc46ea9756e90b7950dca68) for nearest-neighbor dispersion, to check whether SFT/DPO data or training reduces output-space spread before code-specific metrics are interpreted.

## Context: The experiment requires a controlled corpus of generated programs. Method: For each problem, we will generate K=100 programs per model, yielding 2,100 total programs per model×prompt configuration. We will use temperature=1.0 without nucleus sampling for consistency. Synthesis: This creates a consistent sample of model outputs for diversity analysis.

### Support

The strongest support for the proposed K=100, execution-based controlled corpus comes from [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), which sampled n=100 programs per APPS task, executed them against unit tests, and used the resulting CORRECT/WRONG labels to train rankers; this directly validates that 100 executable programs per problem can be generated, labeled, and analyzed, although it used temperature 0.8 for Codex and 0.9 for GPT-J and GPT-Neo, 512-token generation, V100-32GB GPUs, and did not measure lexical, syntactic, or semantic diversity. The next strongest support is [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), which generated up to 100 candidate C++ programs per SPoC pseudocode prompt and evaluated them by execution, showing that a 100-sample executable corpus is feasible and that sampling temperature and duplicate avoidance affect success, with sampling without replacement improving pass rates by 2.0 and 2.3 percentage points on testp and testw and UniqueRandomizer being more than twice as fast as Monte Carlo i.i.d. sampling on a GPU for a 12-line prompt. Direct methodological support for the proposed pairwise average distinctness metric comes from [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), which computed Sim@K, CSim@K, and DPass@K over K=10 generated codes using token, embedding, and reasoning similarity, found that higher temperature tended to lower similarity and thus increase diversity, and showed that conditioning on functional correctness changed CSim@10; although K=10 is smaller than the proposed K=100, the metric is the inverse of the proposed average pairwise distinctness and supports measuring lexical, syntactic, and semantic diversity in code. The same paper also supports the planned prompting comparison because few-shot chain-of-thought and planning prompting increased Sim@10, meaning they reduced diversity, so zero-shot, two-shot, and chain-of-thought templates are likely to produce measurable differences. Broader support for controlled sampling corpora and diversity-quality tradeoffs comes from [(Holtzman et al., 2019-04)](https://www.semanticscholar.org/paper/cf4aa38ae31b43fd07abe13b4ffdb265babb7be1), which generated 5,000 GPT-2 Large passages under beam, full, top-k, nucleus, and temperature sampling, used HUSE with k=13 and human typicality, and showed that nucleus sampling had the highest HUSE while full sampling produced incoherent text; this supports the need for a fixed sampling protocol and for execution-based correctness safeguards in code. Support for execution-based behavior analysis also appears in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), which sampled large pools of programs, clustered candidates by behavior, and evaluated pass@k and 10@k, showing that behavior-based filtering improves solve rates, although its 100k to 1M sample budgets are much larger than K=100. Additional support for controlled sample sets and execution harnesses comes from [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), which generated 20 or 200 programs per ParEval prompt at temperature 0.2 or 0.8 with nucleus p=0.95 on an A100 80GB GPU and evaluated pass@k plus performance, and from [(Khatry et al., 2023-05)](https://www.semanticscholar.org/paper/ab9485a6564cdbe5b5ce2233d5b00c64ceaa518c), which used high-temperature candidates, optional temperature-0 candidates, execution-output grouping, and semantic interleaving to improve top-K execution-match accuracy. Weaker but relevant support includes [(Grubisic et al., 2024-02)](https://www.semanticscholar.org/paper/c78f70c011de0024f110f67e911953e8ef086a4b), which compared 100 sampling steps under random, greedy, and nucleus temperatures and showed temperature sensitivity; [(Xie et al., 2023-05)](https://www.semanticscholar.org/paper/ef018d9fad6167cfddb7d6654c5422df1e953730), which varied temperature gamma in stochastic reasoning generation and showed diversity-related effects on accuracy; [(Liu et al., 2023-12)](https://www.semanticscholar.org/paper/41113411e748a34bb80f12c761b7af1ed6dbb90), which treats diversity as a controlled variable in instruction-tuning data selection but not generated code; and more indirect context from [(Vilnis et al., 2022-10)](https://www.semanticscholar.org/paper/c505b1abb840c8477b35a4503834e04241ffa7b5), [(Deng et al., 2022-12)](https://www.semanticscholar.org/paper/66476832701361c9f9b2a7eb2354ee8cd9f72e67), and [(Luo et al., 2023-06)](https://www.semanticscholar.org/paper/454c8fef2957aa2fb13eb2c7a454393a2ee83805), which use controlled generation or execution-based evaluation but do not directly test the proposed diversity metrics. The proposed use of problem-level Wilcoxon Signed-Rank tests and Cohen's D is also stronger than the descriptive reporting in several related works, which often omit p-values and confidence intervals.

### Contradictions

The strongest contradiction to the proposed fixed temperature=1.0 without nucleus sampling is evidence that high-temperature or untruncated sampling can reduce coherence and quality: [(Holtzman et al., 2019-04)](https://www.semanticscholar.org/paper/cf4aa38ae31b43fd07abe13b4ffdb265babb7be1) found that full sampling produced the least coherent text, including an invented word, while nucleus and top-k sampling achieved higher HUSE after distribution smoothing, and that high temperature or high k was needed to match Zipfian diversity but caused unnaturally high perplexity; for code, this suggests temperature 1.0 without nucleus may increase lexical variety but may also increase syntactic invalidity, runtime errors, or semantically wrong outputs, confounding diversity with failure. A strong code-specific contradiction comes from [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), which used lower temperatures, 0.8 with replacement and 0.4 without replacement, and showed that sampling without replacement improved executable success by 2.0 and 2.3 percentage points over i.i.d. sampling, indicating that the proposed protocol, which does not explicitly remove duplicates and uses temperature 1.0, may waste part of the K=100 budget on duplicates or low-quality programs and may underestimate effective semantic diversity. The proposed K=100 budget is also contradicted by the scale of behavior-space exploration in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), where 100k samples solved 31.8 percent of validation and 29.6 percent of test CodeContests problems and 1M samples with clustering solved 34.2 percent of validation problems, implying that 100 samples may capture only a small portion of the behavior space, especially for hard competitive-programming tasks, and that nucleus sampling and metadata variation were used to improve diversity and correctness. Additional contradictions or cautions come from [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), which used temperature 0.8 with nucleus p=0.95 and 200 samples for larger-k metrics, suggesting that temperature 1.0 without nucleus and only 100 samples is an unvalidated, potentially noisier regime for pass@k-style execution evaluation; from [(Khatry et al., 2023-05)](https://www.semanticscholar.org/paper/ab9485a6564cdbe5b5ce2233d5b00c64ceaa518c), which combined high-temperature sampling with an optional temperature-0 candidate and semantic interleaving, implying that high temperature alone may not produce the most useful diverse top-K outputs; and from [(Grubisic et al., 2024-02)](https://www.semanticscholar.org/paper/c78f70c011de0024f110f67e911953e8ef086a4b), where nucleus sampling at temperatures 1.2 or 1.4 was most effective in an LLVM optimization setting, although this is domain-specific and not a direct test of code diversity. A further limitation is the small problem set: the proposed 21 problems are far smaller than the 50 problems in [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), 164 HumanEval tasks in [(Luo et al., 2023-06)](https://www.semanticscholar.org/paper/454c8fef2957aa2fb13eb2c7a454393a2ee83805) and [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), 677 SPoC problems in [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), and 13,328 training plus 117 validation and 165 test CodeContests problems in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), so the planned 2,100-program corpus per model and prompt configuration may be too narrow to support broad claims about instruction tuning. Indirect cautions also come from [(Xie et al., 2023-05)](https://www.semanticscholar.org/paper/ef018d9fad6167cfddb7d6654c5422df1e953730), where increased stochasticity did not always improve accuracy and could underperform on low-diversity commonsense tasks, and from [(Deng et al., 2022-12)](https://www.semanticscholar.org/paper/66476832701361c9f9b2a7eb2354ee8cd9f72e67), which used temperature 0.4 with nucleus p=0.95 for Codex seeds rather than temperature 1.0 without nucleus, showing that low-temperature truncated sampling can be effective for generating useful executable programs.

### Suggested Action

The most important action is to add duplicate control and report effective sample size: because [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99) showed that sampling without replacement improved executable success and because duplicates can artificially depress lexical, syntactic, and semantic diversity, the method should either use unique sampling, post-hoc deduplicate exact and near-duplicate programs, or report duplicate rates and compute diversity on both raw and deduplicated K=100 corpora. The second most important action is to ablate sampling settings rather than treating temperature=1.0 without nucleus as a fixed constant: include at least temperature 0.4, 0.8, and 1.0, with and without nucleus p=0.95, and optionally a temperature-0 candidate, because [(Holtzman et al., 2019-04)](https://www.semanticscholar.org/paper/cf4aa38ae31b43fd07abe13b4ffdb265babb7be1), [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), [(Grubisic et al., 2024-02)](https://www.semanticscholar.org/paper/c78f70c011de0024f110f67e911953e8ef086a4b), and [(Khatry et al., 2023-05)](https://www.semanticscholar.org/paper/ab9485a6564cdbe5b5ce2233d5b00c64ceaa518c) all show that temperature and truncation materially affect diversity, coherence, and executable correctness. Third, increase or validate the sample budget: run a K saturation study with K=10, 100, 200, and if feasible 500 or 1000, and use behavior clustering or output clustering as in [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5) and [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) to determine whether K=100 captures stable semantic diversity, especially for hard problems. Fourth, strengthen the execution protocol: classify each program as correct, wrong, crash, timeout, or parse error, compute semantic diversity on all executable outputs and separately on correct outputs, and use Docker resource limits, timeouts, and deterministic test ordering, following the execution-labeled corpus design in [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), the executable success evaluation in [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), and the output-based semantic grouping in [(Khatry et al., 2023-05)](https://www.semanticscholar.org/paper/ab9485a6564cdbe5b5ce2233d5b00c64ceaa518c). Fifth, expand the problem set beyond 21 or at least stratify the 21 problems by difficulty, test-case count, and expected solution space, and explicitly compare base, SFT, DPO, and PPO+DPO checkpoints on the same problems and prompt templates, because related work use larger and more varied benchmarks such as APPS, HumanEval, MBPP, SPoC, CodeContests, and ParEval, as in [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), [(Luo et al., 2023-06)](https://www.semanticscholar.org/paper/454c8fef2957aa2fb13eb2c7a454393a2ee83805), [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), and [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), while [(Liu et al., 2023-12)](https://www.semanticscholar.org/paper/41113411e748a34bb80f12c761b7af1ed6dbb90) shows that diversity-aware instruction-tuning data selection is relevant but does not directly measure generated-code diversity. Sixth, make the diversity metrics more directly comparable to prior code-diversity work by reporting Sim@K, CSim@K, and DPass@K-style aggregates alongside EAD, AST Distinct-N, CodeBERTScore, and ICE-Score, and validate at least one neural or reasoning-based similarity measure with a small human annotation set as in [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c). Seventh, improve statistical rigor by using problem-level paired Wilcoxon Signed-Rank tests with Cohen's D, confidence intervals, multiple-comparison correction, fixed random seeds, and sensitivity analyses for prompt templates, because many related works report descriptive gains without p-values or confidence intervals, such as [(Shi et al., 2020-02)](https://www.semanticscholar.org/paper/c860d1560cf495895f931e09ffd698f77ede5b99), [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), and [(Luo et al., 2023-06)](https://www.semanticscholar.org/paper/454c8fef2957aa2fb13eb2c7a454393a2ee83805). Finally, document reproducibility details that are critical for the corpus: model checkpoints, API versions, max tokens, stop sequences, batch size, GPU or API cost, Docker image, test-case counts, and false-positive rate, following the level of detail in [(Inala et al., 2022-06)](https://www.semanticscholar.org/paper/075b6fb7d3787953164eecc1bd2e13f97c9f3c44), [(Li et al., 2022-02)](https://www.semanticscholar.org/paper/5cbe278b65a81602a864184bbca37de91448a5f5), [(Nichols et al., 2024-01)](https://www.semanticscholar.org/paper/dd6fc92208929798bfa4bf6050a3ee5c0febc555), and [(Deng et al., 2022-12)](https://www.semanticscholar.org/paper/66476832701361c9f9b2a7eb2354ee8cd9f72e67).

## Context: Base and instruction-tuned models may respond differently to prompts. Method: We will test three prompt templates (zero-shot, two-shot, two-shot with chain-of-thought) to account for different model capabilities and ensure fair comparison between base and instruction-tuned models. Synthesis: This controls for prompt effects that could otherwise be mistaken for tuning effects.

### Support

The strongest support comes from [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da00af443643bda), which directly treats prompt format as a controlled factor across standard zero-shot, zero-shot chain-of-thought, few-shot chain-of-thought, and self-consistency decoding on 12 reasoning datasets, including GPT-3 175B in original and instruction-tuned forms, GPT-J 6B, and PaLM 540B. Its quantitative results show that prompt template can change behavior far more than model capability alone, with MultiArith accuracy rising from 17.7 to 78.7 under zero-shot chain-of-thought, GSM8K rising from 10.4 to 40.7, cross-task few-shot chain-of-thought reaching 39.0 on AQUA-RAT and 88.2 on MultiArith, and PaLM 540B zero-shot chain-of-thought reaching 66.1 and 43.0 on two reported arithmetic tasks versus 25.5 and 12.5 under zero-shot. This supports the proposed plan because if prompt template can alter reasoning traces, then comparing base and instruction-tuned code models under only one template could mistake prompt sensitivity for tuning-induced diversity change. A closely related and slightly older line of evidence is [(Wei et al., 2022-01)](https://www.semanticscholar.org/paper/1b6e810ce0afd0dd093f789d2b2742d047e316d5), which showed that chain-of-thought exemplars more than doubled GSM8K performance for large GPT and PaLM models, while smaller models did not benefit and sometimes performed worse than standard prompting, and that PaLM 540B reached state-of-the-art results on GSM8K, SVAMP, and MAWPS; this supports testing chain-of-thought as a separate condition but also warns that two-shot chain-of-thought may interact with model scale. The next strongest support is code-oriented: [(Guo et al., 2024-02)](https://www.semanticscholar.org/paper/46a294a1ddc43517a9ad11d05da7af1e93e91a39) compares 0-shot and 3-shot random, retrieved, re-ranked, and oracle prompts for Mistral-7B, CodeLlama-7B, CodeLlama-13B, and Llama-2-13B on API Pack, using bge-large-en-v1.5, bge-reranker-large, SequenceMatcher threshold 0.9, and 1,128,599 instances, finding that fine-tuned models benefit from 3-shot retrieved while non-fine-tuned models improve substantially from 0-shot to 3-shot; this directly supports separating prompt effects from tuning effects in code generation, although it uses 3-shot rather than the proposed two-shot. The foundational evidence is [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0), which showed that zero, one, and few-shot prompting changed GPT-3 performance across Winogrande, OpenBookQA, PIQA, ARC, and word-manipulation tasks, with few-shot K typically 10 to 100 in a 2048-token context, supporting the need for multiple prompt conditions. Code summarization work by [(Jin et al., 2023-12)](https://www.semanticscholar.org/paper/22b261bf190b630c53e57f300a379fb834c69b22) also supports prompt-template control in code tasks by comparing zero-shot, few-shot, and chain-of-thought prompting on 557,664 binary functions with 320 candidate prompts, temperature 0.1, top_p or top_k set to 1, and reporting zero-shot as the best technique when performance and cost are jointly considered, with semantic similarity 0.474 for source code and 0.118 for raw bytes. Weaker but relevant support comes from [(Madusanka et al., unknown_d)](https://www.semanticscholar.org/paper/17560ad9f94218d0953dcec8c1c3b7e5bf4fb7bc), where standard versus chain-of-thought prompting in zero-shot model checking changed LLaMA output consistency and quantifier-specific accuracy on 72K train and 36K test instances, and from [(Liu et al., 2021-07)](https://www.semanticscholar.org/paper/28692beece311a90f5fa1ca2ec9d0c2ce293d069), which shows prompt-induced majority-label, recency, and common-token biases in BART, T5, and GPT-2 answer prediction. More recent prompt-construction work by [(Jin, and Lu, 2024-09)](https://www.semanticscholar.org/paper/46648c014df998c2c57bc6971db36c6a5830afdf) supports model-dependent prompt effects by showing that GPT-4o zero-shot chain-of-thought reached 92.3 on GSM8K versus 90.9 for few-shot chain-of-thought, while ECHO matched few-shot chain-of-thought on GPT-3.5-Turbo-0301. The weakest support is from [(Li et al., 2023-05)](https://www.semanticscholar.org/paper/d4b250b67454a889a68e1a813eb844b85005b1f7) and [(Wu et al., 2024-08)](https://www.semanticscholar.org/paper/311afad89f513f0edc89bd6c762c87de15ab1952), which show that prompt formulation and few-shot or chain-of-thought conditions matter in medical QA and visual pattern recognition, but they do not measure code diversity or base versus instruction-tuned LLMs. Although none of these works directly measures lexical, syntactic, semantic, or neural code diversity, the pattern of evidence supports the proposed prompt-control rationale.

### Contradictions

The strongest contradiction is that the proposed three-template design may be too narrow to ensure fair comparison, because prompt effects are not uniform across model scale, task, demonstration format, and decoding strategy. [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da00af443643bda) shows that zero-shot chain-of-thought can outperform few-shot chain-of-thought on some tasks, while few-shot chain-of-thought with cross-task examples can outperform zero-shot chain-of-thought on MultiArith, and model-scale analysis shows performance is mostly flat without chain-of-thought but increases sharply with it for larger models; therefore a fixed two-shot chain-of-thought condition may not capture the relevant prompt effect for base versus instruction-tuned code models. [(Wei et al., 2022-01)](https://www.semanticscholar.org/paper/1b6e810ce0afd0dd093f789d2b2742d047e316d5) reinforces this by showing that chain-of-thought benefits are scale-dependent and that smaller models sometimes perform worse than standard prompting, so two-shot chain-of-thought may confound tuning with the ability to follow reasoning traces. A second strong contradiction comes from newer code work by [(Guo et al., 2024-02)](https://www.semanticscholar.org/paper/46a294a1ddc43517a9ad11d05da7af1e93e91a39), which shows that in code generation the choice among 3-shot random, retrieved, re-ranked, and oracle prompts matters, and that fine-tuning interacts with prompt retrieval; the proposed two-shot condition does not specify whether examples are random, retrieved, task-matched, or oracle, so prompt selection could be mistaken for instruction tuning. [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0) also contradicts the sufficiency of a small fixed prompt set by showing that demonstration count, prompt length, random example sampling, and 2048-token context can materially change GPT-3 outputs, with few-shot K often 10 to 100 and task-dependent gains or flat results. Newer work by [(Jin, and Lu, 2024-09)](https://www.semanticscholar.org/paper/46648c014df998c2c57bc6971db36c6a5830afdf) further contradicts a fixed two-shot chain-of-thought assumption by showing that automated CoT prompt construction, demonstration count, and iteration count matter, and that GPT-4o can perform better with zero-shot chain-of-thought than with few-shot chain-of-thought on GSM8K. [(Jin et al., 2023-12)](https://www.semanticscholar.org/paper/22b261bf190b630c53e57f300a379fb834c69b22) provides a task-specific contradiction to the necessity of few-shot or chain-of-thought prompting in code tasks, because zero-shot was selected as the best prompt engineering technique when performance and cost were jointly considered for binary function summarization, suggesting that adding two-shot or chain-of-thought may change performance without necessarily improving fairness. [(Madusanka et al., unknown_d)](https://www.semanticscholar.org/paper/17560ad9f94218d0953dcec8c1c3b7e5bf4fb7bc) contradicts the assumption that chain-of-thought uniformly improves prompt comparability: standard versus chain-of-thought differences were not substantial for ChatGPT and Flan-T5, while LLaMA under standard prompting failed to follow the instruction by generating both True and False labels, meaning chain-of-thought may primarily alter output format or consistency rather than capability. [(Liu et al., 2021-07)](https://www.semanticscholar.org/paper/28692beece311a90f5fa1ca2ec9d0c2ce293d069) contradicts the idea that simply comparing templates removes prompt bias, because prompt-induced majority-label, recency, and common-token biases require calibration against a context-free prompt. Weaker contradictions include [(Li et al., 2023-05)](https://www.semanticscholar.org/paper/d4b250b67454a889a68e1a813eb844b85005b1f7), where input-length constraints prevented eight-shot prompting for some models, implying that two-shot may not be equally feasible or comparable across base and instruction-tuned models, and [(Wu et al., 2024-08)](https://www.semanticscholar.org/paper/311afad89f513f0edc89bd6c762c87de15ab1952), where zero-shot, few-shot, and chain-of-thought conditions are reported for a 954-item visual benchmark but without enough quantitative detail to show that the proposed three-template set is sufficient.

### Suggested Action

Most important, expand the prompt design from three fixed templates to a factorial prompt-robustness design that includes zero-shot, zero-shot chain-of-thought, two-shot, three-shot or four-shot random, retrieved, task-matched, and oracle demonstrations, and explicitly model prompt by tuning interaction; this is motivated by [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da00af443643bda), [(Wei et al., 2022-01)](https://www.semanticscholar.org/paper/1b6e810ce0afd0dd093f789d2b2742d047e316d5), and [(Guo et al., 2024-02)](https://www.semanticscholar.org/paper/46a294a1ddc43517a9ad11d05da7af1e93e91a39), which show that shot count, chain-of-thought, retrieval, and model scale can change outputs. Second, standardize prompt length, example selection, answer format, and system versus suffix instructions across base and instruction-tuned models, and report prompt-conditioned diversity rather than averaging over prompts, because [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0) and [(Guo et al., 2024-02)](https://www.semanticscholar.org/paper/46a294a1ddc43517a9ad11d05da7af1e93e91a39) show that prompt length and demonstration source affect performance and output distribution. Third, measure and condition on instruction-following validity, such as whether the model emits parseable code, follows the requested function signature, or avoids mixed-label style failures, because [(Madusanka et al., unknown_d)](https://www.semanticscholar.org/paper/17560ad9f94218d0953dcec8c1c3b7e5bf4fb7bc) shows that base models can fail standard prompts while chain-of-thought changes consistency; the plan should report failure rates and compute diversity on valid programs separately. Fourth, separate chain-of-thought reasoning text from final code before computing lexical, syntactic, and semantic diversity, and report length, pass@1, execution success, and diversity conditional on correctness, because chain-of-thought can add unnecessary steps or rephrase the question as noted by [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da00af443643bda) and can alter token and AST statistics. Fifth, use mixed-effects models or repeated-measures analyses with random effects for problem, model, prompt, and seed, rather than only Wilcoxon Signed-Rank tests and Cohen's D, to account for the 21 problems, K=100 samples, three or more prompts, and multiple model families, following the statistical reliability approach in [(Wu et al., 2024-08)](https://www.semanticscholar.org/paper/311afad89f513f0edc89bd6c762c87de15ab1952). Sixth, add prompt-bias controls such as a neutral or context-free prompt baseline and calibration checks, inspired by [(Liu et al., 2021-07)](https://www.semanticscholar.org/paper/28692beece311a90f5fa1ca2ec9d0c2ce293d069), to ensure that diversity differences are not driven by prompt-induced label or format bias. Seventh, include a pilot study to verify that the proposed EAD, AST Distinct-N, execution-based semantic distinctness, CodeBERTScore, and ICE-Score metrics respond to prompt template changes independently of correctness, and report hardware, API versions, decoding parameters, context length, token counts, and cost, as done in [(Jin et al., 2023-12)](https://www.semanticscholar.org/paper/22b261bf190b630c53e57f300a379fb834c69b22) and [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0); keep temperature=1.0 without nucleus sampling for the primary diversity estimate, but also report a greedy or low-temperature correctness control.

## Context: Semantic diversity requires executing generated programs safely. Method: We will execute all generated programs in isolated Docker containers for safety, extract relevant functions and imports, and compute diversity scores across all test cases. Synthesis: This operationalizes execution-based semantic diversity and enables automatic evaluation of generated code.

### Support

The strongest support for executing generated programs in isolated Docker containers comes from [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f), which used a sandboxed Docker container with JUDGE0 on an AWS EC2 m7i.large instance to run 1,380 unique Python problems against public and private CodeNet and AlphaCode tests and recorded runtime and memory usage; it also compared base and instruction-tuned models, with CodeLlama base 46.4 versus instruct 22.5 pass@1, DeepSeekCoder base 45.4 versus instruct 35.2, CodeGemma base 48.2 versus instruct 43.9, and StarCoder2 base 41.5 versus instruct 49.8, showing that execution-based metrics can differentiate base and instruction-tuned models and motivating the planned paired comparisons, although it did not measure diversity. This extends the earlier Docker harness of [(Yu et al., 2023-02)](https://www.semanticscholar.org/paper/6ab8aca8f631f42760a86cc614dfd7208b3fe58e), which used Linux Docker images, pyenv and venv for project-specified Python versions, Java 17, static call graphs, branch-coverage-guided test augmentation, and standalone NewTestFile programs to compare actual and expected outputs for 230 CoderEval problems with 10 samples per problem; that work supports the proposed extraction and replacement idea and shows that output comparison is feasible, although it used Pass@K rather than diversity. The extraction component is further supported by [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a), which extracted target functions, dependencies, and import information for 355 repository-level samples and executed generated code against tests with 92.46 percent line coverage, and by [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a), which used LLM sandboxing to preserve context, mock external APIs, simulate file access, and generate at least three executable tests with at least three asserts, achieving 95.76 percent line coverage; these newer works show that function and import extraction and dependency handling can be automated, which is necessary for the proposed extraction of relevant functions and imports. The iterative sequence also includes [(Siddiq et al., 2023-11)](https://www.semanticscholar.org/paper/c6649c4247282c3e46593e26c5e0429fcb7c7673), which used prompt-specific Dockerfiles and unittest classes for functional and security behavior, and [(Wang, 2024-08)](https://www.semanticscholar.org/paper/953c3f6a63c687fee7af2520d70d25b3ad1e885e), which executed generated Java snippets in the CoderEval Docker environment for 230 tasks, both supporting containerized test execution but at smaller or more specialized scope. Finally, [(He et al., 2024-02)](https://www.semanticscholar.org/paper/399edc3a101e6f538d95c39db017c7a39445ab49) supports execution-based automatic signals by executing generated tests on HumanEval-X with 10 outputs at temperature 0.2 and measuring assertion accuracy and coverage, although it did not use Docker or diversity scoring. Overall, the literature supports the feasibility of the proposed Docker execution, function and import extraction, and test-output capture, but none directly supports pairwise semantic diversity scoring.

### Contradictions

The strongest contradiction is not to Docker itself but to the assumption that execution outputs across existing test cases are sufficient for semantic diversity: [(Yu et al., 2023-02)](https://www.semanticscholar.org/paper/6ab8aca8f631f42760a86cc614dfd7208b3fe58e) found that standalone functions were generated substantially more successfully than non-standalone functions while more than 70 percent of open-source functions were non-standalone, and it required static call graphs and manual branch-coverage-guided test augmentation to make tests reach target functions; this implies that the proposed extraction of relevant functions and imports may fail or produce many non-executable programs unless the harness handles project-level dependencies, and that test outputs may miss semantic differences not exercised by the selected tests. This is an iterative limitation because later Docker-based work such as [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) and [(Wang, 2024-08)](https://www.semanticscholar.org/paper/953c3f6a63c687fee7af2520d70d25b3ad1e885e) builds on Yu's execution harness but exposes resource and coupling issues that Yu did not address. The next strongest limitation is dependency and coupling confounding: [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a) showed performance decreased with longer targets, more function calls, and external libraries, and required mocking external APIs and local file simulation; [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a) showed full-size context and dependency invocation mattered, and [(Wang, 2024-08)](https://www.semanticscholar.org/paper/953c3f6a63c687fee7af2520d70d25b3ad1e885e) showed coupling fan-out affected Pass@K differently for GPT-4 and GPT-3.5, so the proposed 21 canonicalized problems must stratify by target length, imports, coupling, and external dependencies or semantic diversity may reflect difficulty rather than instruction tuning. Safety and resource constraints are also contradicted by the need for stronger isolation: [(Siddiq et al., 2023-11)](https://www.semanticscholar.org/paper/c6649c4247282c3e46593e26c5e0429fcb7c7673) used prompt-specific Dockerfiles and sandboxing to prevent unsafe behavior, and [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) recorded runtime and memory usage, indicating that a generic Docker container without network restrictions, timeouts, CPU and memory limits, and JUDGE0-style resource accounting may be insufficient for K=100 programs at temperature 1.0. A further contradiction is that most related execution studies used lower sampling temperatures and fewer samples, e.g., [(He et al., 2024-02)](https://www.semanticscholar.org/paper/399edc3a101e6f538d95c39db017c7a39445ab49) used 10 outputs at temperature 0.2, [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a) used 10 to 20 samples at temperature 0.3 and top-p 0.95, [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a) used 10 outputs at temperature 0.2 and top-p 0.95, and [(Wang, 2024-08)](https://www.semanticscholar.org/paper/953c3f6a63c687fee7af2520d70d25b3ad1e885e) used temperature 0, so the proposed K=100 at temperature 1.0 without nucleus sampling is not directly validated and may increase invalid or low-quality programs; [(Yu et al., 2023-02)](https://www.semanticscholar.org/paper/6ab8aca8f631f42760a86cc614dfd7208b3fe58e) reported only 10 samples and about 1 percent standard deviation for Pass@K, while [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) did not report significance tests, and the planned 21 problems is much smaller than 1,380, 355, 230, or 164 problems used in related work, so problem-level variance may dominate the planned Wilcoxon and Cohen's D comparisons.

### Suggested Action

The most important action is to make the semantic-diversity harness coverage- and dependency-aware before scoring: use static call graphs or AST analysis to extract the target function and imports, build standalone wrappers or project-level stubs, mock external APIs and file access as in [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a), and augment the 21 problems with branch- and line-coverage-guided tests as in [(Yu et al., 2023-02)](https://www.semanticscholar.org/paper/6ab8aca8f631f42760a86cc614dfd7208b3fe58e) and [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a), reporting coverage per problem and treating unreachable or untested branches as a validity limitation. Next, harden Docker execution using prompt-specific images or a JUDGE0-style sandbox on a specified instance such as AWS EC2 m7i.large, with network disabled, CPU and memory limits, timeouts, and captured stdout, return values, exceptions, and compilation failures, following [(Waghjale et al., 2024-07)](https://www.semanticscholar.org/paper/eb0db181546bd8493246d8f767b63d57ca4e686f) and [(Siddiq et al., 2023-11)](https://www.semanticscholar.org/paper/c6649c4247282c3e46593e26c5e0429fcb7c7673); define a canonical output representation so that identical outputs across all test cases count as semantically equivalent, while errors and timeouts are separate classes. Third, control for confounds by stratifying or regressing on target length, number of function calls, imported libraries, coupling fan-out, and context length, using evidence from [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a), [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a), and [(Wang, 2024-08)](https://www.semanticscholar.org/paper/953c3f6a63c687fee7af2520d70d25b3ad1e885e), and report results by problem difficulty and model family. Fourth, validate the K=100, temperature=1.0, no-nucleus sampling plan with a pilot on a subset of models and problems, because related work mostly used 10 to 20 samples at lower temperatures [(He et al., 2024-02)](https://www.semanticscholar.org/paper/399edc3a101e6f538d95c39db017c7a39445ab49), [(Xie et al., 2024-03)](https://www.semanticscholar.org/paper/02db2f2522478afc0d109c0a0cfacefeb6fbb27a), [(Hai et al., 2024-06)](https://www.semanticscholar.org/paper/7914f1a628d6078bcafa1e1bef13db0a0282ad0a), and [(Yu et al., 2023-02)](https://www.semanticscholar.org/paper/6ab8aca8f631f42760a86cc614dfd7208b3fe58e); if invalid-code rates are high, either report diversity among executable programs and among all programs separately or use a temperature and top-p grid. Fifth, strengthen statistical analysis by using the planned Wilcoxon Signed-Rank tests and Cohen's D but adding multiple-comparison correction, permutation tests for pairwise diversity, and effect-size confidence intervals, and by correlating semantic diversity with lexical EAD, syntactic AST distinctness, CodeBERTScore, and ICE-Score to test whether execution-based diversity captures distinct semantic variation. Finally, include a small human validation subset to check that programs with different test outputs are perceived as semantically distinct, since none of the cited works directly validates semantic diversity scoring.

## Context: The study needs inferential tests for the planned comparisons. Method: We will conduct paired statistical tests using Wilcoxon Signed-Rank Tests and Cohen's D effect sizes to compare:
1. Base models vs. instruction-tuned counterparts
2. Small vs. large models within families  
3. Zero-shot vs. few-shot prompting effects
4. Different instruction tuning methods (SFT vs. preference tuning)
Synthesis: This provides the statistical analysis for determining whether observed diversity differences are meaningful.

### Support

Strongest support for the proposed paired inferential framework comes from [(Su et al., 2021-09)](https://www.semanticscholar.org/paper/841ca3d87a422451596b8a4b8350e92106971791), which used a nonparametric paired Sign Test at p < 0.05 to compare PPTOD base and SOLOIST on 50 MultiWOZ 2.0 test sessions rated by five graders on 0-to-2 Likert scales, with Fleiss kappa ranging from 0.598 for truthfulness to 0.806 for fluency; this supports the broader idea that paired nonparametric tests can evaluate model-output differences, although it used a Sign Test rather than Wilcoxon Signed-Rank and did not report Cohen's D. The next strongest support is [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), which directly studies code-generation diversity using pairwise Sim@K, CSim@K, and DPass@K over K=10 sampled programs on 50 APPS and 50 HumanEval problems, showing that higher temperature lowers Sim@10 and CSim@10 while few-shot chain-of-thought and planning-based prompting increase Sim@10; this supports the plan's pairwise diversity framing, correctness-filtered diversity, and zero-shot versus few-shot prompting contrasts. [(Zeng et al., 2024-03)](https://www.semanticscholar.org/paper/d503e569c94a4d689a576bb994744adc49aef505) strongly supports the planned base-versus-instruction-tuned and prompt-format contrasts in executable code, because it evaluates base, instruction-tuned, and continued-pretrained CodeLlama variants on the same CoderUJB Java tasks and reports that CodeLlama-Instruct-13B dropped 39.39% in pass-all@k=1 and 31.05% in pass-all@k=10 relative to CodeLlama-13B, while CodeLlama-Instruct-34B showed mode collapse in pass-syntax@k=1 and pass-all@k; however, it uses descriptive comparisons rather than Wilcoxon Signed-Rank tests or Cohen's D. [(Hendrycks et al., 2021-05)](https://www.semanticscholar.org/paper/1ccd031f28dccfb226f6c0c588c93a97a50bf95f) supports the executable-code setting and the need to compare model scale, fine-tuning, and few-shot prompting, using APPS with 10,000 problems, 131,777 test cases, beam width 5, strict accuracy, test-case pass rate, and syntax-error frequency, and showing that GPT-3 few-shot had about 59% syntax errors versus about 3% for GPT-Neo, while smaller fine-tuned models could outperform larger few-shot models. [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da06af443643bda) supports the importance of prompting and scale interactions, with zero-shot chain-of-thought raising MultiArith from 17.7 to 78.7 and GSM8K from 10.4 to 40.7, but it is descriptive and does not test diversity. Finally, [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0) provides older, broader evidence that model scale and prompting change performance, with GPT-3 125M to 175B evaluated zero-shot, one-shot, and few-shot in 2048-token contexts, but it reports only point estimates and does not address code diversity or inferential tests.

### Contradictions

Strongest contradiction to the plan's metric assumptions is from [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c), which found that embedding-based CodeBERT similarity had weak or non-significant correlation with human similarity judgments, approximately 0.50, while reasoning-based LLM-Eval correlated up to 25% higher; this contradicts relying on CodeBERTScore or ICE-Score alone to capture semantic diversity without validation. The next strongest contradiction is that instruction tuning does not uniformly reduce code-generation quality or diversity: [(Zeng et al., 2024-03)](https://www.semanticscholar.org/paper/d503e569c94a4d689a576bb994744adc49aef505) found instruction tuning improved automated program repair for most instruction-tuned models, and CodeLlama-Instruct-7B and 13B had syntactic correctness similar to base models, with the 13B pass-all drop attributed to solution quality rather than parse failures, so the hypothesis that instruction tuning broadly causes mode collapse must be tested rather than assumed. [(Hendrycks et al., 2021-05)](https://www.semanticscholar.org/paper/1ccd031f28dccfb226f6c0c588c93a97a50bf95f) contradicts the assumption that larger or few-shot models will produce cleaner diversity signals, because few-shot GPT-3 generated introductory APPS solutions with about 59% syntax errors while GPT-Neo had about 3%, and GPT-2 0.1B Top-5 test-case average 10.75 exceeded GPT-2 1.5B Top-1 7.96, showing that candidate sampling, fine-tuning, and syntax validity can confound diversity if not filtered. [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da06af443643bda) contradicts a simple zero-shot versus few-shot contrast by showing that prompting format and model scale interact strongly, with zero-shot chain-of-thought outperforming few-shot chain-of-thought on MultiArith at 78.7 versus 27.0 and on AQUA-RAT at 33.5 versus 31.9, so prompting effects cannot be interpreted without controlling for prompt type and scale. [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0) provides weaker contradictory evidence that prompting effects are non-monotonic and potentially contaminated, with one-shot performance dropping by half or more on character manipulation tasks and a noted filtering bug leaving benchmark overlap, while reporting no p-values or effect sizes. [(Su et al., 2021-09)](https://www.semanticscholar.org/paper/841ca3d87a422451596b8a4b8350e92106971791) does not directly contradict the Wilcoxon plan, but its use of a Sign Test on only 50 sessions and five graders shows that small paired human-evaluation samples can yield limited power, warning that 21 problems may be insufficient for reliable Wilcoxon Signed-Rank tests across multiple metrics.

### Suggested Action

First, pre-register the inferential unit and statistical protocol: treat each of the 21 problems as the paired observation for base-versus-instruction-tuned, small-versus-large, zero-shot-versus-few-shot, and SFT-versus-preference contrasts, compute per-problem diversity scores from K=100 samples, use Wilcoxon Signed-Rank with exact p-values, report 95% confidence intervals and paired Cohen's d_z or Hedges g, and apply Holm or Bonferroni correction for multiple metrics and contrasts; because n=21 is small, add a power analysis, bootstrap or permutation confidence intervals, and consider expanding to at least 50 problems if resources allow, following the paired nonparametric logic in [(Su et al., 2021-09)](https://www.semanticscholar.org/paper/841ca3d87a422451596b8a4b8350e92106971791). Second, validate the diversity metrics before using them as primary outcomes, especially CodeBERTScore and ICE-Score, by evaluating a stratified subset of 100 to 200 code pairs with human raters and reporting Pearson or Spearman correlations, as [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) found CodeBERT weak and LLM-based reasoning evaluation stronger; make execution-output semantic diversity the primary metric and report lexical EAD, AST-based syntactic diversity, and neural scores as secondary. Third, control for syntax and correctness by reporting syntax-error rates, pass@k, strict accuracy, and test-case pass rates, and compute diversity on syntactically valid and functionally correct subsets using CSim@K or DPass@K, following [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) and [(Hendrycks et al., 2021-05)](https://www.semanticscholar.org/paper/1ccd031f28dccfb226f6c0c588c93a97a50bf95f), so that invalid or mode-collapsed programs do not confound diversity, as observed in [(Zeng et al., 2024-03)](https://www.semanticscholar.org/paper/d503e569c94a4d689a576bb994744adc49aef505). Fourth, structure the experimental contrasts to avoid confounds: compare base and instruction-tuned models only within the same family and parameter size, use matched SFT checkpoints for SFT versus preference tuning, keep temperature=1.0 and no nucleus sampling fixed but report seeds, max tokens, Docker isolation, and API versions, and analyze prompt templates as a factor rather than a single zero-shot versus few-shot contrast, because [(Kojima et al., 2022-05)](https://www.semanticscholar.org/paper/e7ad08848d5d7c5c47673ffe0da06af443643bda) and [(Zeng et al., 2024-03)](https://www.semanticscholar.org/paper/d503e569c94a4d689a576bb994744adc49aef505) show prompt format and scale interact. Fifth, add sensitivity analyses for sampling temperature and candidate count, since [(Chon et al., 2024-08)](https://www.semanticscholar.org/paper/5db9709ceb0a81b7dfc741e9fe309f32a53d6d8c) showed temperature changes Sim@10 and [(Hendrycks et al., 2021-05)](https://www.semanticscholar.org/paper/1ccd031f28dccfb226f6c0c588c93a97a50bf95f) showed Top-5 sampling can change evaluated performance; if K=100 is costly, report K=10 and K=100 stability. Sixth, decontaminate and document the 21 CodeNet-derived problems, filtering training overlap as warned by [(Brown et al., 2020-05)](https://www.semanticscholar.org/paper/90abbc2cf38462b954ae1b772fac9532e2ccd8b0), and report dataset size, test-case counts, hardware, hyperparameters, and baseline comparisons to improve reproducibility.
